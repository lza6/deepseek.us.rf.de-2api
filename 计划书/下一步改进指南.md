## 2. 第一性原理：项目的根本矛盾

**本质**：这不是"翻译一个标准 API"，而是**把一个有状态、单点、限速、需人机验证的浏览器协议，伪装成无状态、高并发、标准的 LLM API**。

由此推出四条不可回避的物理约束：

1. **认证昂贵且串行**：Turnstile 求解一次 45–65s，是唯一慢路径。→ 必须"一次求解、长期复用、失效自愈"。
2. **任何一次聊天需要 2 次上游往返**（cache_key + SSE），且 cache_key 一次性。→ 单请求无法"零延迟"。
3. **上游是单一 bot（bot_id=27623），provider 固定 DeepSeek**。→ **不存在真正的"多模型路由"**；所有模型别名只是同一个 bot 的壳。
4. **cf_solver 是单点，每 10 分钟重启一次，约 30–35s 不可用**。→ 必须有熔断/重试/降级，否则周期性地全站 502。

**改造的胜负手**：把"昂贵认证"的复用率、把"单点求解器"的可用性、把"协议伪装"的诚实度，三件事做到生产级。

### 3.1 P0 阻断级

#### P0-1 Docker 默认无鉴权暴露 0.0.0.0 ⚠️安全 —— ✅ 已修复（2026-10-06）

- **现象**：`docker run` 时若未设 `API_KEYS`，网关监听 `0.0.0.0:47833` 且**放行所有请求**。
- **证据**：`Dockerfile:18` `ENV LISTEN_ADDR=0.0.0.0:47833`；`auth.rs:13-15` 空 `api_keys` 恒 `Ok(())`；`config.example.json:9` `"api_keys": []`。
- **根因**：安全默认值只在"本机监听"假设下成立（`main.rs:44` 仅打印警告），但 Dockerfile 把监听地址改成全网卡，破坏了"仅本机放行"的隐含前提。
- **影响**：网关一暴露即成为开放代理，可被滥用刷上游配额（违反 ToS）。
- **方案**：启动时校验——若 `api_keys` 为空 **且** `listen_addr` 非 loopback，**拒绝启动**（fail-fast），错误信息明确指引设置 `API_KEYS`。保留显式逃生阀 `ALLOW_INSECURE_PUBLIC=1`（供深知风险者）。
- **落地**：`config.rs` 新增 `validate_security()`/`validate_security_with()` + `host_is_loopback()`（支持 `localhost`/127.0.0.0/8/`[::1]`）；`main.rs` 启动前调用，失败 `eprintln` + `exit(1)`。
- **验收（已实测）**：`0.0.0.0` 无 key → 退出码 1 + 中文错误；`0.0.0.0`+key / 回环 / `ALLOW_INSECURE_PUBLIC=1` → 正常启动（`/healthz` 200）。
- **工作量**：S（已完成）

### 3.2 P1 高优先级

#### P1-1 `ts_required` 自愈是"假实现" ⚠️与宣传严重不符 —— ✅ 已修复（2026-10-06）

- **现象**：`README.md:18`（架构图"Cookie 池 + 自愈"）、`CHANGELOG.md:14`、`RELEASE_NOTES.md:7,10` 均宣称"`ts_required` 自动重新求解"；实际**没有任何自动重试**。
- **证据**：
  - 非流式路径（`api.rs:162-165`）：识别 `__TS_REQUIRED__` → 直接 `return Err(AppError::TsRequired)` → 给客户端 502，**不重试**。
  - 流式路径（`api.rs:142-146`）：`__TS_REQUIRED__` 被当普通错误文本，作为 `data:` 帧塞进 OpenAI 流 → 客户端收到 `{"error":{"message":"__TS_REQUIRED__"}}` 的**流内错误**，比 502 更糟（OpenAI 客户端解析失败）。
  - `upstream.rs:365`（cache_message）遇 403 直接返回 `TsRequired`，无重取。
- **根因**：`ensure_authed`（`upstream.rs:176`）只在"cookie 缺失或 TTL 过期"时刷新，**没有强制失效路径**（无 `force_reauth()`）；也没有"捕获 ts_required → 清 cookie → 重认证 → 重试一次"的控制流。
- **影响**：生产运行中 cookie 提前失效时，**直到 TTL 到期前所有请求持续失败且不自愈**，与文档承诺矛盾。
- **方案**：
  1. `UpstreamClient` 新增 `force_reauth()`：清空 `cookies`/`nonce`/`cookie_obtained`，置 `solving=false` 后调用 `ensure_authed()`。
  2. `api.rs` 抽出 `start_stream_with_retry()`：捕获 `TsRequired`（含流内首个事件）→ `force_reauth()` → **重试 1 次**（仅 1 次，避免风暴）。
  3. 流式路径：把 `__TS_REQUIRED__` 单独识别为 `TsRequired`，触发重试或向客户端发标准 `error` 事件后正常结束（不得静默塞入 delta）。
- **落地**：`upstream.rs` 新增 `force_reauth()`；`api.rs` 拆分 `start_stream`（探测首事件 + 强制重认证重试 1 次，重试时换新 `chatcmpl-` id）与 `start_stream_once`（单次启动）。仅当**首事件**为 `__TS_REQUIRED__` 时才重试——此时尚未向下游输出，无重复内容风险。
- **验收（已实测）**：新增集成测试 `ts_required_triggers_reauth_and_retry`——mock 上游首个 cache_key 返回 `ts_required`、第二次返回正常流；断言网关自动重认证并返回 200 + 完整内容（非 502）。全量测试 42 单测 + 10 集成全绿。
- **真实 E2E 验收（已实测，`scripts/e2e-selfheal.mjs`）**：真实上游 + 真实 cf_solver。首次 SSE 注入真实抓包的 `ts_required` → 网关日志出现「上游要求重新安全校验，强制重认证后重试」→ `force_reauth` 真实重新求解（token 709）→ 真实兑换 `{"ok":true}` → 重试转发真实上游 → 真实回复 `¡Hola!`（HTTP 200）。
- **工作量**：M（已完成）

#### P1-2 `provider` 模型路由是"假实现" ⚠️ —— ✅ 已修复（2026-10-06）

- **现象**：`/v1/models` 列出 6 个模型（`deepseek-es`、`-openai`、`-claude`、`-google`、`-openrouter`、`-xai`），注释声称"按 provider 路由"（`models.rs:30`、`README.md:118` "按 provider 路由"）。
- **证据**：`api.rs:199-207` `start_stream(...)` 的参数名为 `_model_id`、`_meta`（下划线=未使用）；`upstream.rs:335-344`（cache_message）与 `394-415`（stream_chat）的请求参数里**从不包含 model/provider**，只有 `bot_id`。`分析文档/05` §0 实测：本站 `provider="DeepSeek"`，**唯一 bot_id=27623**；§3 明确"前端不暴露模型 ID"。
- **根因**：把"上游 bot 的 provider 是服务端配置项、代理无法切换"这一事实，误实现为"暴露多个别名即等于多路由"。
- **影响**：用户选 `deepseek-es-claude` 实际仍走 DeepSeek，**输出与期望不符**；`/v1/models` 宣称的 `context_window`/`vision`/`web_search` 能力为虚构。
- **方案（二选一，推荐 A）**：
  - **A（诚实收敛，推荐）**：`/v1/models` 只保留**真实存在的单模型**（`deepseek-es`），或在别名上显式标注 `alias_of: "deepseek-es"`、`routable: false`，并在文档删除"按 provider 路由"表述。
  - **B（真路由，成本高）**：若确需多模型，必须**配置多个 bot_id（多个站点 bot）**，`models.rs` 目录改为"bot_id → 模型"映射，请求时把对应 bot_id 透传（`cache_message`/`stream_chat` 已按 bot_id 走，只需让 bot_id 随模型变化）。**注：目前只有一个 bot，B 需先探测/新增 bot，暂不可行。**
- **验收**：`/v1/models` 返回的每个条目都能真实路由到对应上游；随机选 2 个模型发请求，验证行为/上游 bot 与声明一致（或明确标注等价）。
- **工作量**：S（方案 A）

#### P1-3 上游配额耗尽未映射为 429 / 死变体 `QuotaExhausted` —— ✅ 已修复（2026-10-06）

- **现象**：上游配额耗尽时返回 SSE `error` + `quota_notice`（`PROTOCOL.md:62-67`），网关把它当普通文本错误 → 客户端拿到 502 而非 429，无法正确退避/换 Key。
- **证据**：`errors.rs:22,55` 定义了 `QuotaExhausted` 且映射 429，但**生产代码零处构造它**（grep 仅见定义与测试）；`protocol/openai.rs:244-258` 的 `translate_event` 只处理 `error`/`ts_required`，**不解析 `quota_notice`**。
- **根因**：错误协议解析漏了上游的配额分支。
- **影响**：配额场景下客户端无退避信号，反复打空请求。
- **方案**：`translate_event` 解析 `data.quota_notice` 存在 → 新增 `Translated::Quota(String)` → `api.rs` 映射 `AppError::QuotaExhausted`（429）。
- **验收**：新增单测（含 `quota_notice` 的 error 事件 → `Quota`）+ 集成测试（mock 返回 quota → HTTP 429 + `error.type=rate_limit_error`）。
- **工作量**：S–M

#### P1-4 `ensure_authed` 并发等待存在逻辑缺陷 —— ✅ 已修复（2026-10-06）

- **现象**：并发首次认证时，若"正在求解"的请求**失败**，其余等待者会立即返回错误，而不会接力重试。
- **证据**：`upstream.rs:200-214`——等待循环里 `if !s.solving { break; }` 跳出后**无条件** `return Err("等待并发求解超时")`，即使对方是"失败结束"而非"成功"。
- **根因**：用轮询 `solving` 布尔量表达"等待他人"，无法区分"他人成功/失败"。
- **影响**：冷启动高并发下，一次求解失败会连带打挂同批请求。
- **方案**：改用 `tokio::sync::Notify` 或 `watch` 通道：求解者完成后 `notify_waiters()`；等待者被唤醒后**重新走双检锁**，若仍无 cookie 则**自己接手求解**（而非返回 Err）。
- **验收**：集成测试——mock solver 首次失败、二次成功；并发 5 请求断言全部最终成功。
- **工作量**：M

#### P1-5 无重试/熔断/背压，cf_solver 单点周期性 502 —— ✅ 已修复（2026-10-06）

- **现象**：cf_solver 每 10 分钟全量重启约 30–35s 不可用（`DEPLOY.md:70-75`），期间网关直接 502；上游网络抖动也无重试。
- **证据**：`upstream.rs` 全流程单次调用，无 retry/backoff；`solver.rs:64-143` 轮询失败仅 `continue` 无退避上限；`api.rs` 无中间件限流。
- **根因**：缺少弹性层（resilience）。
- **影响**：周期的可用性空洞 + 突发流量压垮求解器。
- **方案**：
  1. solver 调用加**指数退避 + 抖动**（上限 3 次）。
  2. 认证路径加**熔断器**（失败 N 次后短时快速失败，冷却后半开）。
  3. 端点加**限流**（`tower-governor` 或令牌桶）+ 有界并发（`tower::limit::ConcurrencyLimit`）。
  4. 文档补充"多 cf_solver 实例 + 故障转移"（可复用上层项目 `solver_guard.py` 思路）。
- **验收**：压测脚本模拟 solver 不可用 → 网关返回 503（非挂起）；恢复后自愈。
- **工作量**：L
