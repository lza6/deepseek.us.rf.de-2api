## 0. 如何使用本指南

1. **严格按版本推进**：`v1.0.0`（正确性加固）→ `v1.5.0`（协议完整）→ `v2.0.0`（能力跃迁）。
   **未完成前一版本的 P0/P1 项，禁止开始下一版本的 P1/P2 项** —— 避免"前面改 bug、后面加功能、又出 bug"的死循环。
2. **每个任务 = 一个原子变更单元**：TDD 先行（每个改动都给定测试用例），完成后跑**定向测试**；版本收尾跑全量：
   ```bash
   cargo test --all
   cargo fmt --all -- --check
   cargo clippy --all-targets -- -D warnings
   ```
3. **验收铁则**：任何声称"已完成"的项，**必须附实际命令与真实输出**。**未实际运行 ≠ 通过**。
4. **禁止重构式改写**：全部为"在现有文件上精准修改/接线/新增"，**不得重写已有模块结构**；`src/protocol`、`src/upstream`、`src/api` 的三层分工保持不变。
5. **不做无证据推断**：凡标 `待验证`，实施前必须实跑验证。
6. **区分"缺陷"与"能力缺口"**：前者是 bug（必须修），后者是上游/协议未覆盖的功能（按版本排期）。本指南已分开标注，不得混为一谈。

## 2. 遗留问题清单（按严重级别，全部带证据）

> 以下条目来自**两轮独立审计 + 本机逐行复验**。严重级别定义：
> **HIGH** = 静默数据损坏 / 主流程高概率错误 / 协议不兼容导致客户端失败；
> **MEDIUM** = 边界缺陷 / 可观测性缺失 / 保护机制弱化；
> **LOW** = 死代码 / 字段冗余 / 风格。

### 2.1 HIGH 级（v1.0.0 必修）

#### H1 · SSE 字节流按 chunk 做 `from_utf8_lossy` —— 多字节字符被静默损坏

**证据**：`src/upstream.rs:650`
```rust
st.buf.push_str(&String::from_utf8_lossy(&b));
```

**根因**：`bytes_stream()` 的 chunk 边界是**任意的**，可能落在 UTF-8 码点中间。
`from_utf8_lossy` 把被截断的半个码点替换为 U+FFFD，下一 chunk 的前导续字节同样被替换 ——
**一个 CJK/emoji 字符被损坏成两个替换符**。

**影响**：上游是西班牙语站点但常服务中文用户，delta 被切在多字节字符中间是**高概率事件**。
这是全部审计项中**唯一会造成静默内容损坏**的缺陷。

**验证方法**（实施前实测）：
```bash
# 写一个 mock 上游，把 "你好" 的 UTF-8 三字节切在 1/2 位置分两个 chunk 发出，
# 断言网关输出仍为完整 "你好" 而非 "�" + "�"。
```

**修复方向**：缓冲**原始 `Bytes`**，只在完整行/事件边界解码。推荐用 `Vec<u8>` 累积，
`find` 定位 `\n\n` 的字节偏移后再切片用 `std::str::from_utf8`；不完整尾字节留在缓冲区。

**验收标准**：新增回归测试 `sse_multibyte_split_across_chunks` 通过；真实 E2E 中文回答无 `�`。

#### H2 · 多轮对话历史被整体丢弃（标准 OpenAI 客户端）

**证据**：`src/protocol/openai.rs:70-101`（`messages_to_prompt` 只取最后一条 user + system）
```rust
let last_user = req.messages.iter().rev()
    .find(|m| m.role == "user").map(|m| m.text())
    .ok_or_else(|| AppError::BadRequest("缺少 user 消息".into()))?;
```
+ `src/api.rs:202-210`
```rust
let session_key = req.user.clone().or_else(|| headers.get("x-session-id")...);
let (_sid, conv_uuid) = state.sessions.get_or_create(session_key.as_deref());
```

**根因**：标准 OpenAI 客户端**每轮把完整消息历史发来**；网关只把最后一条 user 送上游，
历史交给上游 `conversation_uuid` 记忆。若客户端未设 `user`/`x-session-id`（**绝大多数 OpenAI SDK 默认不设**），
`get_or_create(None)` **每次生成随机 conv_uuid**，上游视为全新会话 ——
于是**整个对话历史被静默丢弃**，模型只看到最后一句话。

**影响**：与 OpenAI 语义**严重不符**。任何多轮对话客户端（Cursor/Continue/LobeChat 等）在未显式设 `user` 时，
第 2 轮起即丢失上下文。

**自证矛盾**：`分析文档/07-2API代理实现指南.md §5.4` 自己承认"需多轮上下文 → 固定 conversation_uuid"，
但**默认路径并未固定**。

**验证方法**：mock 上游记录收到的 `conversation_uuid`；
连续发两轮不含 `user` 字段的请求，断言两次 conv_uuid **相同**（当前实现是**不同**）。

**修复方向（二选一，推荐 A）**：
- **A**：当请求含多轮历史时，把全部历史按角色拼入 prompt（`[user] ... \n[assistant] ... \n[user] ...`），
  而非只取末条 —— 使网关自身无状态、每轮独立可复现。
- **B**：为无 `user` 的请求派生**稳定的** `conv_uuid`（如对首条 user 文本做哈希），
  但这样不同用户的首条相同会串扰，故需配合 A 使用。

**验收标准**：新增测试 `multi_turn_history_preserved`（断言 prompt 含全部历史轮次）；
新增 `conv_uuid_stable_without_user_field`（若采用 B）。

#### H3 · Anthropic 端点的 HTTP 级错误体是 OpenAI 结构

**证据**：`src/errors.rs:64-75`（**唯一的** `IntoResponse`）
```rust
let body = serde_json::json!({
    "error": { "message": self.to_string(), "type": self.error_type(), "code": self.error_type() }
});
```

**根因**：`/v1/messages`、`/v1/messages/count_tokens` 的**所有** `AppError`（401/400/429/502…）
都经此返回 `{"error":{...}}`。Anthropic 规范要求：
```json
{ "type": "error", "error": { "type": "invalid_request_error", "message": "..." } }
```
Claude Code / Anthropic SDK 解析错误时会**失败**。

**自证不一致**：流内错误事件用的是**正确**的 Anthropic 结构（`api.rs:657-676`），与 HTTP 级错误不一致。

**验证方法**：`curl -X POST /v1/messages -d '{}'`（缺 messages），断言响应体含 `"type":"error"` 顶层字段。

**修复方向**：在 Anthropic 处理器中把 `AppError` 显式转为 Anthropic 错误体（新增 `anthropic_error_response()`），
或引入响应包装类型区分协议族。**不要**改动全局 `IntoResponse`（会破坏 OpenAI 端点）。

**验收标准**：新增测试 `anthropic_error_body_is_anthropic_shaped`；Claude Code 实测错误可读。

### 2.2 MEDIUM 级（v1.0.0 – v1.5.0）

#### M1 · CRLF / CR 行尾在**流级**分帧不被识别

**证据**：`src/upstream.rs:619`（`st.buf.find("\n\n")`）vs `src/upstream.rs:670`（`parse_block` 有 `strip_suffix('\r')` 且有 CRLF 单测 `upstream.rs:711-715`）

**根因**：`parse_block` 支持 CRLF 并有单测，但流级分隔符**硬编码为 `"\n\n"`**。
若上游用 `\r\n\r\n`（SSE 规范允许），`find("\n\n")` **永不命中**，缓冲区累积到流结束，
`parse_block` 把**整个响应当作一个块**解析 → 事件全部塌缩。

**现状**：当前真实上游用 `\n`（E2E 确认），故为**潜在**缺陷；但现有 CRLF 单测给出**虚假信心**。

**修复方向**：按 `\n\n` / `\r\n\r\n` / `\r\r` 任一分割（取最早位置）。
**验收标准**：新增测试 `sse_crlf_block_separator`。

#### M2 · `http_timeout_secs=120` 是**整条请求**（含 SSE body）总超时 → 长回答被截断

**证据**：`src/config.rs:33-35`、`src/upstream.rs:70`
```rust
.timeout(Duration::from_secs(cfg.http_timeout_secs));
```

**根因**：reqwest 的 `timeout` 覆盖从建连到 **body 读完**的全过程。
流式生成超过 120s 会触发 body 读取错误 → `parse_sse_stream` 走 `pending_err`（`upstream.rs:652-655`）
→ 下游收到 `__stream_error__` 而非正常结束。**无独立 connect / read-idle 超时**。

**修复方向**：改用 `read_timeout`（reqwest 0.12 支持，按两次读之间间隔计），或对 SSE 流单独建不带总超时的 client。
**验收标准**：新增测试模拟慢速长流（>120s 间隔发心跳）不触发截断。

#### M3 · `__TS_REQUIRED__` 内部哨兵值泄漏给下游

**证据**：`src/api.rs:283-287`（流式 OpenAI）、`src/api.rs:711-713`（Anthropic 非流式）
```rust
oai::Translated::Error(e) => json!({"error":{"message":e,"type":"upstream_error"}})
```

**根因**：`start_stream` 只在**首个**事件为 ts_required 时重试一次（`api.rs:517-524`）。
若重试后首个事件仍为 ts_required，或 ts_required 出现在**中途**，则哨兵字符串原样进入 `message` 字段。
**Anthropic 非流式**（`api.rs:711`）甚至不特判，直接 `UpstreamStream("__TS_REQUIRED__")` 返回 502。

**自证不一致**：OpenAI 非流式正确特判（`api.rs:348`），但三条路径行为不一致。

**修复方向**：在翻译层就把 `__TS_REQUIRED__` 转成结构化错误（如 `AppError::TsRequired`），
所有下游路径统一处理，禁止哨兵字符串泄漏。

#### M4 · Anthropic 流式 usage 恒为 0/0

**证据**：`src/api.rs:599-602`、`src/api.rs:645-648`
```rust
input_tokens: 0, output_tokens: 0   // message_start 与 message_delta 均硬编码
```

**根因**：未使用 `estimate_tokens`。Anthropic SDK 依据 `message_delta.usage.output_tokens` 统计用量，
**客户端会看到 0**。对比：非流式已正确估算（`api.rs:726`）。

**修复方向**：`message_start` 用 `estimate_tokens(prompt)`；`message_delta` 用累积输出字符估算。
**验收标准**：新增测试断言流式 usage 非 0。

#### M5 · nonce 失效时只刷新、不重试原请求

**证据**：`src/upstream.rs:495-500`
```rust
if !pr.success {
    if body.contains("nonce") || body.contains("security") { let _ = self.refresh_nonce().await; }
    return Err(AppError::Upstream(format!("缓存失败: {body}")));   // ← 刷新后仍返回错误
}
```

**根因**：刷新了 nonce 却**立即返回错误**，本次请求仍失败（502）。
`分析文档/06 §2.2` 明确前端行为是"刷新 nonce **后重试原请求**"。
同理 `stream_chat` 拿到非 2xx（含 403）直接 `AppError::Upstream`（`upstream.rs:548-550`），
未映射为 `TsRequired`、未触发刷新重试。

**修复方向**：`cache_message` 检测到 nonce 类失败时，刷新后**递归重试一次**（带幂等保护）。

#### M7 · 上游中途断开时下游信号不完整

**证据**：
- OpenAI：`src/api.rs:300-307` **无条件**追加 `[DONE]`，但 `stop_chunk`（带 `finish_reason`）仅在收到 `Translated::Done` 时发出（`api.rs:279-282`）→ 断开时下游收到 `[DONE]` 却**无 finish_reason**。
- Anthropic：`src/api.rs:631-655` 仅在 `Done` 时发 `message_delta`/`message_stop` → 断开时流直接结束，**无 message_stop**，客户端视为异常截断。

**修复方向**：上游断开（`Err` 或非正常结束）时，下游应发**带错误 finish_reason 的结束事件**，
保证协议完整（OpenAI: `finish_reason:"error"` + `[DONE]`；Anthropic: `message_delta` + `message_stop`）。

#### M8 · `auth_lock` 头阻塞：一次求解期间所有并发请求排队

**证据**：`src/upstream.rs:237`
```rust
let _guard = self.auth_lock.lock().await;
```

**根因**：`do_auth` → `solve_with_retry`（`upstream.rs:299-324`）最坏耗时 `solver_timeout(120s) × (solver_retries+1)`。
期间**所有**需要认证的并发请求在 `auth_lock` 上排队。

**死锁分析**：**无死锁**（锁序恒为 `auth_lock → state`，无环）。
但延迟叠加严重，且**无 TokenPool / 预取**（`分析文档/07 §5.3` 建议但未实现）。
TTL 到期后的首个请求会**内联阻塞 45-65s+**。

**修复方向**：后台预取（TTL 到期前 10% 主动刷新），或引入"求解中"标记让等待者快速失败并提示重试。
**验收标准**：压测：cookie TTL 到期瞬间的 10 并发请求，P99 延迟不应 ≈ 10× 求解耗时。

#### M9 · 熔断器半开状态放行**全部**并发探测

**证据**：`src/upstream.rs:266-276`
```rust
if let Some(t) = b.open_until {
    if Instant::now() < t { return false; }
    b.open_until = None; b.consecutive_failures = 0;   // 半开：无单探测门限
}
```

**根因**：冷却到点后**清空状态即放行**。此时 N 个并发请求会**同时**打到 cf_solver 单点。
教科书式半开应**只放行一个探测请求**。另：半开后一次失败只把计数从 0 增到 1（`upstream.rs:284-296`），
需**再次累计到阈值**才重开，期间会重复 120s 求解尝试 —— 保护滞后。

**修复方向**：半开态引入 `probe_in_flight: bool`，只允许一个请求通过。
**验收标准**：新增测试 `half_open_allows_single_probe`。

---

#### M10 · 流式路径的配额耗尽返回 HTTP 200 + 错误帧，而非 429

**证据**：`src/api.rs:288-292`（OpenAI 流）、`src/api.rs:663-668`（Anthropic 流）

**根因**：非流式正确映射 429（`api.rs:353/714`，测试 `quota_exhausted_returns_429`），
但流式**已在 200 响应内**，无法改状态码，配额错误被写成 `{"error":{"type":"rate_limit_error"}}` 的 data 帧。
SDK 通常**不会**把它当限流处理。此外流首帧 `first_chunk`（`api.rs:244-253`）在配额错误之前先发出。

**现状**：SSE 协议固有限制（响应头已发出）。**缓解**：在流**开始前**预检（若上游能在首事件前暴露配额），
或确保流**首帧即为 quota 错误**（当前实现已接近，需强化顺序）。

#### M11 · `max_response_bytes` 仅约束 OpenAI 非流式

**证据**：`src/api.rs:341`
```rust
if full.len() + t.len() > state.cfg.max_response_bytes { return Err(...) }
```

**根因**：Anthropic 非流式聚合（`api.rs:705-717`）**无上限**，可被超大上游响应撑爆内存。
流式路径无上限属固有限制，但 Anthropic 非流式**应与 OpenAI 对齐**。

**修复方向**：抽取共享的聚合函数，两处统一上限检查。

#### M12 · 未知/非文本上游事件静默丢弃，无日志/无指标

**证据**：`src/protocol/openai.rs:271-273`
```rust
// message_start / status / citations / grounding_metadata / display_form_event / warning
_ => None,
```

**根因**：上游共 **8 种命名事件**（`分析文档/03 §5`），网关只翻译 3 种（`message`/`done`/`error`）。
其中 `warning` 事件携带 `{"error":"..."}`（**非致命警告**，前端会追加到消息），此处连同
`status`/`citations`/`grounding_metadata`/`display_form_event` 一起**丢弃**。

**现状**：本站（provider=DeepSeek）当前不触发，但**无兜底日志/计数器** ——
未来上游新增事件类型会被**完全静默吞掉**，不可观测。

**修复方向**：对未识别事件记 `debug` 日志 + 计数器（供 `/admin/api/status` 展示）。
**验收标准**：新增测试 `unknown_event_is_logged`（断言计数器 +1）。

## 6. 架构扩展建议（进阶方向）

### 6.1 认证层：从"内联阻塞"到"后台预取"

**现状**：`ensure_authed` 在 TTL 到期时**内联**求解（`upstream.rs:233-243`），最坏阻塞 45-65s（见 M8）。

**建议**：引入后台刷新任务（`tokio::spawn` 定时器），在 cookie 剩余 TTL < 20% 时主动续期。
`ensure_authed` 的快速路径直接命中新鲜 cookie，无需等待。

```
[现状] 请求 → cookie 过期 → 持有 auth_lock 求解 60s → 返回
[目标] 后台任务提前 20% TTL 续期 → 请求 → 直接命中新鲜 cookie → 毫秒返回
```

**风险**：后台任务需与优雅关闭（`main.rs:98`）协调，避免 shutdown 时悬挂。

### 6.2 协议层：引入"协议族"抽象

**现状**：`errors.rs` 的 `IntoResponse` 是**全局唯一**的，导致 Anthropic 端点错误体错误（H3）。

**建议**：定义 `trait Protocol`，`OpenAiProtocol` / `AnthropicProtocol` 各自实现
`error_response(&AppError) -> Response`、`stream_event(...)`、`nonstream_body(...)`。
处理器按端点选择协议实现，**消除当前散落在 `api.rs` 里的 if-else 协议分支**。

**注意**：这是**结构性改动**，需评估 `api.rs`（801 行）的拆分代价。
**建议在 v1.5.0 之后**、有独立测试网兜底时再做，且**不得破坏现有 23 个集成测试**。

### 6.3 可靠性：SSE 解析的字节级状态机

**现状**：`parse_sse_stream`（`upstream.rs:597-663`）用 `String` + `find("\n\n")`。

**建议**：改为**字节级状态机**（`Vec<u8>` 缓冲 + 扫描 `\n\n`/`\r\n\r\n`），
在完整事件边界才做 `from_utf8`。一次性解决 H1（UTF-8 损坏）+ M1（CRLF）。
这是**最根本的修复**，优先于其他 SSE 相关改动。

### 6.4 可观测性：指标暴露

**建议**至少暴露以下指标（供 Prometheus 抓取或 `/admin/api/status` 展示）：
- `gateway_requests_total{endpoint,status}`
- `gateway_upstream_latency_seconds{phase}`（auth / cache_message / stream）
- `gateway_solver_solve_seconds{instance}`
- `gateway_unknown_sse_events_total`（对应 M12）
- `gateway_breaker_state`（0=closed / 1=open / 2=half-open）

### 6.5 性能：响应缓存的语义化

**现状**：`ResponseCache::key(model, prompt)` 是**无会话语义**的纯文本哈希（`cache.rs`）。
仅对"无会话历史"的请求启用（`api.rs:209`）。

**建议**：
- 引入 `temperature == 0` 才缓存的策略（非确定性请求不应缓存）。
- 缓存键纳入 `system_prompt_suffix`（否则改动 suffix 后旧缓存仍命中）。
- 考虑语义缓存（embedding 相似度），但需评估误命中风险。

### 6.6 安全：分层防御加固

| 建议 | 理由 |
|------|------|
| `/admin` 增加**独立**限流（当前不限流，`api.rs:42` 注释明示） | 防本地高频轮询/爆破 |
| `admin_token` 支持**哈希存储**（当前明文比对） | 防止配置文件泄露即令牌泄露 |
| 下游 key 支持**过期时间** | 当前 `api_keys` 是静态白名单 |
| 审计日志（谁、何时、用了哪个 key、多少 token） | 账本已有基础，可扩展为安全审计 |

### 8.4 已知外部约束（不可通过改代码解决）

- **cf_solver 间歇失败**：Turnstile 求解成功率约 1/3，10 分钟强制重启上下文（~30-35s 不可用）。
  -> 缓解：多 solver 实例（已支持）+ 熔断（已支持）。
- **上游 SSE 无 `id:` 行 + `cache_key` 一次性** -> **无法**实现真正的上游 `Last-Event-ID` 续传。
  当前是网关侧同进程内存重放（`replay.rs`），进程重启/缓冲过期返回 409。**已在 README 如实披露。**
- **单一上游 bot**（`bot_id=27623`，provider 固定 DeepSeek）-> 无法切换 provider，故只暴露 1 个真实模型。
- **上游不暴露模型 ID / 不支持 tools / 联网 / 上传**（`分析文档/05 §0`）。
